## 03. Analisis Teknis & Pilihan Solusi (Trade-Offs)

### 03.01 Mekanisme Migrasi Basis Data di PHP Native
- **Opsi A (Direkomendasikan): File DDL SQL Terpusat (`schema.sql`) + Runner Eksekusi CLI (`migrate.php`)**
  - *Kelebihan:* Sangat transparan, mudah di-audit, tidak membebani sistem dengan dependensi migration tool pihak ketiga, dan dapat diimpor langsung via phpMyAdmin Laragon maupun dieksekusi sekali jalan melalui CLI.
  - *Kekurangan:* Membutuhkan disiplin dokumentasi manual jika terjadi alter skema di tahap berikutnya.
- **Opsi B: Migration Framework Berbasis File Terpisah (seperti Phinx / Doctrine Migration)**
  - *Kelebihan:* Mendukung rollback bertingkat otomatis.
  - *Kekurangan:* Menambah dependensi Composer pihak ketiga yang melanggar prinsip *Strict PHP Native*.
- **Keputusan:** Mengadopsi **Opsi A** dengan runner mandiri `database/migrate.php` dan skrip DDL `database/schema.sql`.

### 03.02 Pengelolaan Koneksi Database (PDO Lifetime)
- **Opsi A (Direkomendasikan): Singleton Pattern via `App\Core\Database::getConnection()`**
  - *Kelebihan:* Efisien memori. Hanya membuka 1 koneksi database per HTTP lifecycle request, mencegah kehabisan connection pool MySQL (*max connections error*).
  - *Kekurangan:* Perlu penanganan reset koneksi jika dijalankan pada unit test jangka panjang.
- **Opsi B: Inisialisasi Instance PDO Baru Setiap Query/Repository**
  - *Kelebihan:* Isolasi total antar query.
  - *Kekurangan:* Boros koneksi dan menurunkan performa aplikasi web.
- **Keputusan:** Mengadopsi **Opsi A** dengan pola *Singleton Connection Manager*.

### 03.03 Tipe Data Moneter & Tanggal
- **Uang (Harga & Subtotal):** Menggunakan `DECIMAL(15, 2)` (bukan `FLOAT`/`DOUBLE`) untuk mencegah galat pembulatan desimal (*precision issue*) pada transaksi keuangan.
- **Jadwal Sewa:** Menggunakan `DATE` untuk rentang sewa harian (`start_date`, `end_date`), dan `DATETIME` untuk rekam waktu pembuatan/transaksi (`created_at`, `paid_at`).
